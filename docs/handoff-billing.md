## Corrections made after the usage cutoff

Actual transfers may omit `environment`, and a queried customer may legitimately have a different `original_app_user_id` after aliasing. The server trusts the API-key-authenticated subscriber lookup for each known local UUID; webhook account identifiers only select accounts to refresh. It processes original/alias/redemption accounts and both transfer sides. Each normalized purchase still must match the configured environment, product allowlist and entitlement purchase period. Unknown/deleting accounts are not recreated, and transfers update their known source/destination accounts atomically after all provider reads succeed.

Malformed provider subscriber maps, null purchase entries, invalid/future timestamps and oversized/non-JSON replies fail without replacing verified state. Numeric transaction identifiers are normalized safely. Stored states recalculate expiry and filter products removed from configuration. `exportBillingUser(userId)` returns both local environment snapshots even when checkout configuration is disabled, with current expiry and safe management links.

The real Test Store lifecycle check found that an expired subscription can retain a null `unsubscribe_detected_at`. Fresh normalized records and cached status/export views now require current active validity before reporting `renews=true`; an expired uncancelled record reports both `active=false` and `renews=false`. Active grace and explicit cancellation behavior remain intact. Cached views preserve verification/provider/purchase/expiry audit dates and do not rewrite the historical snapshot.

Canonical `sameOrigin` from `lib/http-security.ts` replaces a host-only origin comparison. JSON media types are checked exactly. Stale webhook deliveries can be acknowledged without contacting an unavailable provider; replay markers store only event type/timestamp/disposition, never account IDs. Local account deletion removes both snapshots and rate entries, while provider subscriptions/payment records remain subject to provider management and retention.

The public SDK key keeps its existing `NEXT_PUBLIC_REVENUECAT_WEB_API_KEY` name but is read on the server through `Reflect.get(process.env, 'NEXT_PUBLIC_REVENUECAT_WEB_API_KEY')`, then string-checked and trimmed. Direct public-key reads, including a property read through a `process.env` alias, were frozen into the actual Next.js 16.3.7 Webpack output. The reflective lookup preserves request-time configuration for the authenticated status API. Root verified a compiled standalone build created with one synthetic public key and started with a different synthetic runtime key: the API returned the runtime key and excluded server secrets.

Server verification no longer depends on a public SDK key or optional Offering setting. The server validates its environment, V1 subscriber-read credential, webhook authorization secret and product allowlist separately. With these four fields configured and the public SDK key absent, authenticated webhooks, stored snapshots and empty-body account synchronization work while `billingPublicConfig()` returns the unchanged fully disabled payload: no key, environment, Offering or product list. Invalid/opposite-environment public keys or malformed Offering settings disable checkout without blocking otherwise valid server verification. Missing or malformed server-required settings still fail closed. The public UI and sync route's expected-product validation are unchanged.
